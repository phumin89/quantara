# Remembered owner control and recovery UI

The disabled trading buttons were caused by browser authority, not missing funding consent in the conversation. The owner browser had a remembered viewing session, but its eight-hour in-memory control authority had expired or been lost on owner-service restart. The setup view offered disabled financial buttons and a vague launcher instruction without an available re-verification form. The owner's direction is to avoid repeatedly asking for control during normal use.

Fresh local owner pairing now offers a separate, explicit **remember control on this device for 30 days** option. It is unchecked by default and requires remembered viewing. Successful opt-in persists only the session hash and a bounded control expiry inside the existing encrypted, certificate-protected session record. Matching active owner cookies can retain control after eight hours and restart. No raw session ID or pairing code is saved in that record. Expiry, logout and issuing a new local pairing code revoke authority. Old protected viewing records and old clients remain viewing-only after restart. Rolling back the server ignores the optional new field and restores the earlier fail-closed control behavior.

The trading setup now exposes the shared owner-pairing form when control is unavailable. `Pair Owner Browser.cmd` invokes the existing same-user local pairing console; it does not start activation or financial verification. Re-verification uses the existing fixed HTTPS endpoint and fresh CSRF token, sends one pairing POST, clears the code and reloads authority. No automatic arm, provisioning, reconciliation, order or retry follows pairing. Owner confirmation, current reconciliation and the account's existing deterministic execution checks still govern activation.

The Codex lead owned and reviewed the backend security change. The bounded local UI bridge was unavailable because its configured executable was missing; its supporting worker used the instructed direct fallback for the two assigned UI files. The lead inspected all changed paths and added the shared form, bounded request helper and tests. No owner limits, execution allowlist, binding, financial grant, Stop or RiskEngine were changed by this implementation.

Before the backend patch, two new deterministic checks failed: explicit control disappeared after eight hours and an invalid control-without-remembering request was accepted. Afterward, **45** session/pairing/owner-endpoint checks and **18** separate owner-access checks passed, with zero failures or skips. Existing viewing-only and denied-control paths remain covered. **24** UI checks passed, including the actual setup component's effect/event path from viewing-only through re-verification: it sends only setup GETs, CSRF GET and pairing POST; the real-money activation button remains disabled pending separate owner confirmation. Type checking and production owner/web builds passed.

A synthetic component browser pass used 1440×1000, 820×1180 and 390×844. The control option was unchecked and there was no horizontal overflow. The pass found checkbox labels stacking in the setup container; the form now reuses the existing confirmation-label layout. This is component evidence, not a live owner session or financial activation.

The final phone confirmation showed both checkbox labels on one aligned row with 44 px targets and no horizontal overflow. Owner was deployed before the new web client; both running service images match the built images. The trading page and the owner's HTTPS CSRF endpoint returned HTTP 200. The actual account remained Armed=false, Stop=false and reconciled. No real pairing POST, financial activation, order or cancellation was performed by the agent. The owner must enter the local code, select remembered control and submit, then perform the existing initial financial activation in the browser. Only the local interactive code window is offered as a handoff; no code is read into the agent conversation.
